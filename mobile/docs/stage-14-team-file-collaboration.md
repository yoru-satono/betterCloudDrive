# 阶段 14：团队文件协作与传输

## 交付范围

阶段 14 在团队只读工作区上增加受服务端有效权限控制的基础协作能力，应用版本为 `versionCode=15`、`versionName=0.15.0-stage14`。

- 所有可写团队目录均可新建文件夹并上传文件；系统多选器按原顺序去重，只处理前 100 项。
- 文件和文件夹支持单项重命名、移动及删除；当前目录可长按进入多选，但多选只提供删除。
- 普通文件可从目录、搜索、详情和预览页创建单文件下载任务；不支持文件夹 ZIP 和批量下载。
- 顶层传输页按上传/下载和全部/个人/团队组合过滤，个人与团队任务共用 Room v2、全局串行执行器、UIDT/WorkManager、通知和终态清理。
- 团队预览继续只读，OnlyOffice 仍使用后端签发的 `mobile=true` 配置。

## 权限与状态边界

根目录能力由 OWNER、ADMIN、EDITOR、VIEWER 角色映射，子目录及单项操作按需读取 `/permissions/effective`。`TeamFileActionsStore` 单独拥有目录权限、项目权限缓存、选择集合、文件操作、移动选择器和传输入队反馈；它不修改团队浏览、搜索或预览 Store。操作成功后通过 `AppContainer` 的明确内容变更回调使相关缓存失效，团队上传批次全部离开活动状态后只刷新目标目录一次。

客户端在权限未知或读取失败时关闭写入口；按钮可见性不是授权事实。所有变更仍由后端在团队事务锁内重新校验权限，运行中权限被撤销时返回 403，客户端清除权限缓存并将传输判定为永久失败，不无限重试。退出登录、切换服务器或会话失效会重置团队操作状态并沿用现有任务、临时文件和 SAF 权限清理流程。

## 后端一致性

团队创建、重命名、移动、删除以及上传初始化、秒传和完成阶段使用同一团队事务锁串行化冲突检查。名称会去除首尾空白并限制为 1～255；文件和文件夹共享父目录名称空间。重命名为当前名称、移动到当前父目录为幂等成功，文件夹移动到自身或后代返回稳定的非法目标语义。

批量删除先去重并折叠同时选中的后代，再递归校验整棵活动子树的删除权限，任一节点失败则事务整体回滚。软删除后，目录、搜索、收藏、标签、分享、预览、下载和直接元数据访问都不会暴露已删除祖先下的条目。团队配额释放同时计算当前文件对象和历史版本对象。

## 验收状态

阶段 14 已于 2026-09-04 完成验收。

- 后端、Testcontainers 集成、Web、Tauri、黑盒、可观测性和完整 Docker 栈验证通过。
- KMP 主机测试、国际化门禁、Debug、Release/R8 与 iOS 公共代码元数据编译通过。
- Android 9/API 28 的 29 项设备测试全部通过；Android 14/API 34 完成 30 项设备测试，其中仅按设计跳过低版本专用 WorkManager 用例。
- API 34 真实旅程验证了 EDITOR 创建两级目录、重命名、移动、选择模式删除，以及一次选择两个文件的团队多文件上传。
- 64 MiB 团队上传在完成 40 MiB 后撤销 EDITOR 权限，任务以不可重试的 403 失败并立即清除写权限缓存；恢复权限和进程后复用原上传会话完成剩余分片。
- 同一文件经团队下载链路写入 SAF，最终 MD5 为 `7f614da9329cd3aebf59b91aadc30bf0`，与源文件一致。顶层传输页的方向与个人/团队作用域筛选、UIDT 标记和终态展示均通过。
- 应用相关 Logcat 中未发现崩溃、ANR、通知投递限流、Bearer Token、下载 ticket 或 SAF URI 泄漏；测试用户、团队、对象、设备文件和本地临时资产均已清理。

真实旅程中发现并修复了“团队传输收到 403 后页面仍沿用旧写权限”的缺陷：传输队列现在发布团队权限失效事件，团队操作 Store 会清空项目权限、重新读取团队角色和当前目录有效权限，并将失败原因显示为明确的权限变化提示。
