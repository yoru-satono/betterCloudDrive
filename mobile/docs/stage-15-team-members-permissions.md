# 阶段 15：团队成员与文件权限

## 交付范围

阶段 15 补齐团队成员与文件级权限管理，应用版本为 `versionCode=16`、`versionName=0.16.0-stage15`。

- 团队成员按角色、用户名和用户 ID 稳定分页；所有成员均可查看列表。
- OWNER 可以管理全部非 OWNER 成员；ADMIN 只能添加、调整和移除 EDITOR、VIEWER。
- 团队文件和文件夹详情展示当前用户的有效权限及来源链。
- 具有 `canManage` 的用户可以为具体成员或 ADMIN、EDITOR、VIEWER 角色保存和删除直接权限覆盖。
- 团队根目录继续使用角色基础权限，不创建根目录覆盖；邀请、通知和所有权转让不在本阶段。

## 架构与安全边界

网络层使用独立的 `TeamMembersApi` 和 `TeamPermissionsApi`，对应 Repository 与 `TeamMembersStore`、`TeamPermissionsStore`。成员列表、权限管理目标、来源链和编辑状态不会进入团队浏览 Store。权限变更由 `AppContainer` 转换为明确授权变更事件，使阶段 14 的项目权限缓存、目录和搜索状态按范围失效。

有效权限仍以后端解析为唯一事实来源：同一节点用户覆盖优先角色覆盖，从目标向最近祖先查找，未命中时使用基础角色，OWNER 始终拥有全部能力。保存和删除覆盖后，服务端会在同一事务中重新计算操作者权限；导致操作者失去当前项目 `canManage` 的变更整体回滚。客户端提前阻止明显自锁，但不复制完整继承算法。

成员管理同样由服务端执行最终角色矩阵。ADMIN 不能通过“先选中已有 ADMIN、再降级”的方式绕过限制；OWNER 不能通过普通成员接口修改或移除。退出登录、切换服务器和会话失效会重置两个新 Store，并清除当前权限管理目标。
