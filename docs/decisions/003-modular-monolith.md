# ADR-003：后端采用模块化单体

- 状态：已接受
- 日期：2026-08-20（对既有实现的追认记录）
- 适用范围：后端模块、部署单元、事务和代码依赖

## 背景与约束

系统包含认证、文件元数据、对象存储、团队权限、异步任务、WebDAV 和管理能力，需要清晰边界，但当前团队和部署规模不需要为每个领域维护独立网络服务、协议版本和分布式事务。

许多写操作需要在一个 PostgreSQL 事务中协调用户、文件、权限、任务和 Outbox。过早拆成微服务会把进程内调用变成远程调用，同时增加发布、观测和故障处置成本。

## 决策

后端采用七个 Maven 模块组成的模块化单体，最终由 `betterclouddrive-start` 打包并作为一个 Spring Boot 进程部署。

依赖方向固定为：`common` 位于底层；`dal` 与 `storage` 提供持久化适配；`service` 承担业务规则和事务；`web`、`scheduler` 是入口；`start` 负责装配。下层模块不得反向依赖 HTTP 或调度入口。

模块边界用于代码所有权、依赖控制和测试，不代表独立服务。跨模块调用默认使用进程内接口；跨 PostgreSQL、对象存储、Redis、RabbitMQ 和邮件的操作仍按跨资源一致性处理。

## 考虑过的替代方案

- 单一 Maven 模块：结构简单，但 Controller、业务规则、持久化和对象操作容易相互渗透。
- 按领域拆成微服务：可以独立扩缩和发布，但当前会引入远程协议、服务发现、分布式追踪和数据一致性复杂度。
- 多个可执行 Spring Boot 模块共享数据库：部署更复杂，却仍通过共享表紧耦合，收益有限。

## 后果

- 正面：一个应用制品和一个数据库事务边界，开发、调试和本地集成成本较低。
- 正面：模块职责和依赖方向仍能阻止大部分层间耦合。
- 负面：应用只能整体发布和扩缩，单个领域故障可能影响整个后端进程。
- 负面：模块隔离依赖构建结构和评审纪律，不具备进程级强隔离。

只有出现可量化的独立扩缩、发布自治、故障隔离或团队所有权需求时，才评估抽取服务；抽取前必须先明确数据所有权和网络协议。
