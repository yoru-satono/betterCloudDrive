# ADR-008：服务端返回语义文案键而非自然语言

> 历史桌面说明：文中 Tauri 部分记录当时决策，客户端现已迁移为 Qt；当前边界见 [Qt 桌面开发](../../desktop/README.md)。原决策正文保留追溯。

- 状态：已接受
- 日期：2026-08-20（对既有实现的追认记录）
- 适用范围：API 响应、通知、任务、活动、权限说明和三端本地化

## 背景与约束

Web/Tauri 与 Android 需要独立选择简体中文或英文，并保持错误处理和状态分支稳定。如果服务端返回可展示的中文/英文文本，客户端会依赖服务端语言、难以切换 locale，也可能按易变翻译文本判断业务状态。

仅返回错误码不足以覆盖通知、任务、活动和权限来源等需要参数插值的用户文案。

## 决策

服务端只返回稳定的语义 key 和结构化参数，例如统一响应的 `messageKey/messageParams`，以及通知、任务、活动和权限对象的对应 key/params 字段。服务端不返回自然语言兜底 `message`，也不把异常诊断文本暴露给客户端。

Web/Tauri 与 Android 分别从本地 catalog 渲染当前 locale。业务分支优先使用错误码、对象类型/状态或稳定 key，禁止按中文或英文翻译文本判断。

语义 key 属于跨端协议。重命名 key 或改变参数形状需要后端、Web/Tauri 和 Android 同步发布；当前不提供旧 key 别名或双读。

## 考虑过的替代方案

- 服务端按请求语言渲染文本：集中管理翻译，但客户端离线状态、locale 切换和多端缓存更复杂。
- 同时返回 key 和自然语言 fallback：兼容性较好，但客户端容易重新依赖 fallback，长期形成双重事实。
- 只返回数字错误码：适合错误分支，但无法覆盖丰富业务对象和参数化文案。
- 客户端自行拼接服务端字段：缺少统一术语和可演进的文案协议。

## 后果

- 正面：客户端能独立渲染 locale，服务端日志/异常与用户文案解耦。
- 正面：稳定 key 和参数可以被协议测试覆盖，避免按翻译文本分支。
- 负面：新增或改名 key 必须同步多个 catalog，版本不匹配会显示缺失 key。
- 负面：没有自然语言 fallback，客户端协议兼容要求更严格。
