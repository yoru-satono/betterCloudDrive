# ADR-005：团队文件权限采用最近祖先覆盖

- 状态：已接受
- 日期：2026-08-20（对既有实现的追认记录）
- 适用范围：团队角色、文件权限覆盖、客户端动作和服务端授权

## 背景与约束

团队基础角色 `OWNER`、`ADMIN`、`EDITOR`、`VIEWER` 需要支持目录子树的例外授权，并能针对一个用户或一个角色配置完整能力。权限结果必须可解释、可审计，并在文件移动后重新计算。

如果逐层合并每一个权限位，用户很难判断最终来源，也容易产生“读被父级拒绝、写却被另一层允许”等不一致组合。若用户覆盖在整棵祖先链上永远优先，又会让远端父目录规则越过更近的目录边界。

## 决策

有效权限先取团队基础角色，再从目标文件向根目录逐节点查找覆盖。在同一节点，具体用户的 `USER` 覆盖优先于成员角色的 `ROLE` 覆盖；命中第一条覆盖后立即停止，不继续逐位合并。

因此“最近节点”优先于跨节点的 subject 类型：目标节点的角色覆盖会先于父目录的用户覆盖生效。每条覆盖完整给出读、写、分享、删除和管理五项能力；`canRead=false` 时其余能力必须同时为 false。

OWNER 和团队根目录直接使用基础角色。服务端是授权事实来源；客户端只使用有效权限响应控制 UI，并在 403 后刷新。

## 考虑过的替代方案

- 所有祖先逐位合并：表达能力高，但难以解释、测试和安全审计。
- 用户覆盖跨整条祖先链始终优先：个性化强，但会绕过更近目录的角色边界。
- 仅支持基础角色：实现简单，但不能满足项目目录和敏感子树的差异化权限。
- ACL 累加允许/拒绝：通用性高，但冲突优先级和默认拒绝规则更复杂。

## 后果

- 正面：解析结果只有一个最终覆盖来源，能够返回稳定的 `sourceType`、`sourceChain` 和继承标记。
- 正面：目录规则自然作用于后代，更近节点可以形成清晰边界。
- 负面：不能组合来自不同层级的权限位，部分复杂策略需要新增覆盖记录。
- 负面：移动文件会改变祖先链，缓存权限必须失效。

自锁保护、OWNER 不可覆盖、同团队作用域和审计通知属于该决策的安全约束。若未来引入权限位合并，必须作为替代 ADR 并同步三端行为和迁移策略。
